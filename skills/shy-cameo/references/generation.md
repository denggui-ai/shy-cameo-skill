# 生成执行

按需读：开拍看「开拍条件与范围」；素材问题看「照片与参考」；按宿主选择「Codex 原生」或「Claude Code」；遇故障直接看「失败与中断」。`R` 为编译返回的请求路径；`sidecar.json` 是单张制作与验收记录；本地额度计数不是服务商账单。

## 开拍条件与范围

用户明确“按这套拍”即要求拍当前已确定的五张，沿用有效照片同意和方案确认，不另加固定口令或重复次数确认。只准备、安装、开发、发布、讨论中的“继续”仍停在原任务。先运行 `CLI preflight --workspace WS`，再核对已确认的分镜、角色造型、素材质量、成年与发送同意；缺项时只补对应项。照片里的人如果不是用户，须已向本人说明用途并取得单独同意。

一套默认最多五次调用，多套按本次明确清单合计；失败也可能计次。经典观演可预先允许一次内容不同的观众故事替代，原请求和替代合计最多六次，按 [演唱会替代规则](stage-and-concerts.md) 执行；没有这项授权仍按五次和实际成片交付。定妆表仅在另行明确要求时制作。中断先 `set-status` 核对，结果未知保留 `claimed`，核实后登记；已失败或取消的记录保留，新的补拍另建请求。

## Claude Code

通过已登录 Codex CLI 执行 `CLI generate-set ... --authorized-count 5`。脚本在首张明确失败时取消后四张；超时或没有图片时保持当前张 `claimed` 并暂停。核对实际结果后 `set-record`，再用 `--resume` 仅拍未提交的张。露脸封面机器分低时等待用户比脸：用户说像再续拍，说不像就修改方案另起一套。按 stderr 报进度，停止时由既有后端结束整个进程组，避免子进程继续提交；停止不代表正在进行的请求未计费。

## Codex 原生

### 多套入口

多套先读series-and-projects.md，按project.json中的本次selection逐套使用下文单套流程。project-status只读汇总，不会提交、恢复或证明授权。首图串联仅限各自套图。当前套明确失败后按既有规则处理完该套再暂停下一套；结果未知、素材变化、账本异常立即核对。明确继续后重新记录剩余范围，不重提成功项、不自动补拍失败项。

动画主题沿用以下同一编译与生成流程，不另造通路、不手改request。三组已测样例见 `storyboarding.md`，不以角色国别或虚构年龄增加门。只准备或验证不授权生图；离线测试不证明成片效果。

0. 只有在取得用户明确授权后才执行以下步骤：明确请求拍摄当前套图即可执行固定五张（见本页“开拍条件与范围”），额外定妆表需用户另行要求（见本页“生成临时定妆表”）。单张的 compile 会先校验授权确认；定妆表请求（`compile-sheet` 产出）不含用户照片，生成后用 `CLI attach-sheet` 挂回卡片，不做 frame-check 与 deliver。
1. 先运行 `CLI compile ...`，拿到 `request_path`（绝对路径，下称 R）。
   照片在 compile 之后若被替换或修改，必须重新走授权确认门（consent --photo）并重新 compile；Codex 路径上没有脚本在生成前复查照片。
2. 读取 R，再把字段**逐字**交给内置生图工具：`prompt` 与 R 的 `prompt` 一字不差，`referenced_image_paths` 与 R 的同名字段一致。**不得改写、翻译、增删提示词**（可解析的完整字面量参数按真实字符串逐字比对；未知变量或表达式保持 `unverifiable`）。在 Codex JS 执行环境中，先读取请求，再原样传入参数：

   ```js
   const r = await tools.exec_command({cmd: "cat R"}); text(r.output);
   // 下一次调用：把 R 中的 prompt 与 referenced_image_paths 原样填入
   await tools.image_gen__imagegen({prompt: "<R 的 prompt 全文>", referenced_image_paths: ["<R 中的路径>"]})
   ```

3. 只生成一次；失败不重试；平台拒绝时如实转告。同一个 R 只生成一次；重新 compile 不能用于重试被拒内容。内容实质不同的安全替代方案按 generation.md“内容审核拒绝后的恢复”核对现有授权，另建请求并保留原拒绝记录；原生开发测试仍按本文相应边界记录，不冒充正式CLI交付。
4. 生成的图片在 `$CODEX_HOME/generated_images/...`，不要移动或重新保存；直接把该路径交给 `CLI frame-check` 和 `CLI deliver`（deliver 会按原字节复制进工作区）。套图第 1 张露脸时的比脸见下文“套图”第 4 步。
5. 先运行 `CLI verify --request R`，会按 R 的路径在 `$CODEX_HOME/sessions` 里自动查找本次会话记录。结果 `unverifiable` 表示“无法审计”，须告知具体原因；历史 `unverified` 同义兼容，不改写旧记录。
   Codex 原生与 Claude Code 适配路径采用同一标准：自动发现和显式 `--log` 都须唯一定位一个会话文件中的完整请求读取窗口，比较窗口内全部调用；缺失或不可读日志、多个会话、重复/同批读取导致窗口歧义、动态参数无法解析时均为 `unverifiable`（无法审计）并说明原因，不把其他分镜当篡改。`--log` 应提供完整会话记录，不按匹配 prompt 筛选调用。窗口中多次调用不算单次通过。调用审计不是图片输出来源或服务商计费证明。

两条路径都使用上述会话审计；`exec.jsonl` 只能辅助排查执行过程，不能仅凭结构化输出声明调用已核验。

调用审计依赖可读取且能唯一划界的会话记录；日志形态变化或参数无法解析时如实记为无法审计。

### 套图（Codex 原生，一套 5 张）

前提：用户明确要求拍摄当前已确定的五张套图；无需固定口令或重复说张数。

以下“第1张”和 `index` 都是执行编号。经典观演先把故事②放在 `shots[0]`，仍从 `--index 1` 开始；`story_order` 仅供展示，不绕过首图门。原套默认仍是五次，不能把 `generate-set --authorized-count 6` 当作会自动补图的入口；一次替代另存新请求，并按演唱会规则合计次数与逐张停止。

1. `CLI compile-shot --set-card S --index 1 [--character C]... --photo P... --workspace WS`，按第 2 步逐字生成一次。
2. 立即登记结果：成功时运行 `CLI set-record --set-card S --workspace WS --index 1 --status generated --image <生成图路径>`；被拒或失败时用 `--status rejected` 或 `--status failed`。
3. 第 1 张核实为 rejected 或 failed：账本会把第 2–5 张标为 `cancelled`，`compile-shot` 会拒绝编译它们（`set_cancelled`）。**不得绕过**，如实告诉用户：已登记 1 次提交尝试，其余 4 张没有提交。
4. 第 1 张成功且露脸时，先跑 `CLI likeness-check <第 1 张图> --photo P... --workspace WS`（封面近景与机器比脸，见本页“可选机器比脸”）：`low` 就停下，把第 1 张和本人照片给用户比脸，用户说像再继续（续拍本套），说不像就改方案另起一套；`ok` / `no_face` / `unavailable` 照常继续（`unavailable` 要告诉用户这次没做机器比脸）。之后依次对 index 2、3、4、5 执行 compile-shot → 生成 → set-record，除这次比脸外中途不再询问用户。
5. 这条路径无法在生成前硬拦，只能靠账本与事后审计核对，不得宣称“脚本保证”。

本地生成入口会拒绝同一工作区的重叠操作（workspace_busy），不支持并发生成。新请求另存 reference-hashes.json；旧请求缺少字节记录时需重新编译，不能借旧授权自动重拍。verify/frame-check 记录分别绑定请求与图片；deliver 不接受其他任务或旧格式的 QA 记录。历史 sidecar 不自动升级或改写。

## 照片与参考

拍什么一确定就要照片，一条消息说完：“发一张清楚的正脸照。是你本人，还是已同意的成年人？照片只存在你电脑里，会发给生图服务。照片里的人如果不是你，请先告诉对方要做什么，并取得对方单独同意。”用户说“先不发、先看方案”→ 衣服用场景默认，开拍前再要；同一张照片之后复用。照片若在方案后才到且影响衣服推荐，先说“按你的照片，衣服建议改成××”，用户同意再改。一张就能拍；多给侧脸是否更像尚未对照，不承诺。已有同一张照片（按内容比对）且同意记录有效就沿用，不重复索取；换了照片重新问。体检发现格式损坏则换有效文件，不花额度；检测器缺失说明人工核对，不能当作照片质量通过。说明实际发送的参考清单，不把网页查资料说成传入实景图。

用户给一张氛围图说"照这个感觉拍"：说"图里的光线和色调直接带不过来，我看图后用文字把它的光写进去"；自己看图，用一两句写出主光方向、冷暖和明暗，写进 lighting 与 cinematography，不写 mood_ref、不把图发给生图服务；图来源说不清或图里有未成年人 → 不看图，按下一段选光线风格。
带上宠物（试验）：要宠物照时说"给一张它清楚的照片：它占满画面、睁着眼、看得见全身；有不同姿势的也可以一起发，我挑最清楚的那张用"，目前只用其中 1 张（多张同时参考还没做）；先问"这是你自己的宠物吗？照片会发给生图服务"，确认后用 consent 登记，写进套图卡 `pet`（ref＋kind，如"猫"）；封面必有宠物，默认五张都有它，剧情说得通才空一张；它是来陪你的，用户没说时问一句"它平时更爱被抱着，还是跟着你跑？"，按回答定陪伴方式（写法见 storyboarding.md"带宠物的套图"）；照片里有人手、杂物没关系，不会画进去；它在照片里只占一小块时，裁成只剩它的特写再用（告诉用户"我把照片裁到只剩它"）；照片里有别人的脸 → 请换一张或裁掉。说"效果没保证"。
和宠物过日常（试验，菜单项）：要宠物照与授权同"带上宠物"；看图认出品种体型后确认一句（"它是英短金渐层、偏胖对吧？"）；问"它平时最爱干什么？比如踩你、钻箱子、趴窗台、守着你吃饭"，按回答编一件小事的 5 张；说不上来时按体型给 4 个题材——猫：窗边看雨、周末赖床、钻纸箱搬新家、深夜陪加班；小型犬：周末赖床、出门买早餐、等你下班开门、窝沙发看电影；大型犬：清晨公园遛弯、湖边玩水、露营篝火、雪天第一次撒欢。画面里只有你和它；有人要加角色 → 改走"带上宠物"＋对应玩法。
用户只说"要电影感""要有氛围"、说不出要哪种光时，不让用户自己去找参考图：先从本项目已有成片里挑 4–6 种光线风格（如单灯夜景、冷暖对撞、舞台聚光、烛光暗调、蓝调时刻、高反差布景）拼成一张图给用户选；还没有成片时各用一句话描述让用户选，选中的写进 lighting 与 cinematography。用户自己给的参考图本身不是电影感的（手机随手拍、平光、灰平）不借，直说"借过来会更像手机照"，改从上面的风格里选。

## 身份素材登记

公开测试版仅提供文字选片说明，不附带人物图片。

- 优先清晰、无遮挡、无明显滤镜的原照，正脸便于对照；已有其他角度可补充。不要把两张或三张说成已验证的最低要求，也不要仅因单张或侧脸拒绝准备。
- 记录素材实际覆盖的头向、俯仰、表情与遮挡；只凭目视不写精确角度。目标超出已提供的角度时说明身份效果未验证，可建议补照；用户仍可选择有限次数尝试，不自动增加调用或限制为只拍正脸。
- 仅支持已确认成年、本人或已获主体同意的照片；素材同意、文件质量与身份相似度是不同检查。
- `CLI consent` 会把本次登记素材按原字节存到 `WS/input/originals/<sha256>.*`，在 consent.json 中保留原路径、相对工作区的 archived_path、sha256、尺寸及字节数。副本损坏时停止，不覆盖。重复登记相同字节不重复记录；reset只重置同意记录，不删除原照。
- 历史记录不自动补档，原件不存在时标记缺失，不把另一编码版本默认为同一照片。生成仍使用明确传入的路径；需要从副本恢复时显式使用 `WS / archived_path`（旧绝对路径按迁移规则兼容），并沿用按摘要绑定的同意核对，不静默替换。
- 私有工作区应位于仓库外且不在临时目录；原照、私人日志不进入公开案例、Issue或发布包。

## 实际参考与首图串联

网页查证不等于图片已发送。scene-ref只借环境和光线；mood_ref 已停用，不写；套图卡可写 pet（ref 宠物照路径：工作区内可用相对路径，外部用绝对路径；先 consent 登记，kind 如"猫"），分镜卡写 pet＝这张宠物在做什么，封面必写，其余张不写就不出现（编译会写明"这张没有猫"，防链图带出）；宠物照预算里永不丢，第 1 张后换照会被拒；角色定妆表不等于用户服装结构参考。编译输出的referenced_image_paths是实际清单，预算不足会明确提示丢弃项；关键实景参考被丢弃时先调整可选参考，不声称已使用。

第2–5张串联首图主要保持衣装、妆发和影调，不继承首张构图/地点。跨国场景在setting中明确；换装或跨时间故事按确认描述例外处理。用户要求重拍时参照宿主说明保留合适串联参考，不覆盖旧图。

## 开拍与等待

开拍说明与开始生成在同一条回复，只告知不再确认：“这套5张，每张提交算一次额度，最多5次；第1张失败就停，后面不花。通常6–12分钟。”多套写总数，如“共4套20张，最多20次额度，大约半小时到一小时”，并说明每拍完一套会停下给你看，回“继续”才拍下一套。Codex里每张出来报一句画了什么；Claude Code按stderr进度报“第2/5张…”，每套结束用系统看图打开。叫停用宿主停止按钮或Esc，正在拍的那张可能已算额度。交付时一句话问：“像你吗？角色和感觉对吗？哪张怪或想改直接说。”没答到且记录需要的项，追问一句，不替用户填；任一项答“否”即记rejected，“这套想要的感觉拍出来了吗”一项的回答用record-verdict --goal记录。选旧版、重拍某张都在交付这一步（选版只更新项目索引selected_run_id，验收用record-verdict），不进下一套。

## 失败与中断

说明哪张已提交、哪张未提交、实际返回什么；额度可能计入，不声称已查账单。首张失败取消后四张；中间失败保留其他已授权张，不自动重试。

**内容审核拒绝后的恢复**：先用一句易懂的话说明哪张没有出图、服务返回的实际类别，其余已出图片仍保留；原始错误与request ID留在私有记录。依据记录中明确提供的输入或输出审核阶段说明，未提供时不猜；“具体触发原因未知”不抹掉已经提供的审核阶段。不把猜测说成原因，也不把正常衣装或用户审美偏好一概称为违规。

保留用户可接受的创作目标，主动提出一个内容上确实不同、符合要求的安全替代画面，而非只留下缺图让用户自己解决。例如陪伴套图可用猫与抚摸手的桌面特写，衣装仅由袖口保持连续，不继续描绘原被拒画面的身体构图。说明改变了什么、保留了什么；不能通过同义词、删标签、隐去意图或更换服务重现被拒内容。用户若要求保留原被拒内容并绕过审核，不执行。

新方案符合用户已授予的修改范围与调用上限时，可作为独立新请求执行，不重复索取已有授权；否则先给具体备选，只补真正缺失的选择或授权。余额本身不等于授权。旧拒绝请求保持rejected，新方案另存实际内容、引用与结果，不复用或重置旧账本、不自动恢复首图失败后取消的镜头。新方案再被拒就停止，不形成替代方案循环。返回图片后核对故事作用、主体、衣装连续性及构图；补齐候选不等于用户验收，也不承诺零拒绝率。

**拍摄中的停顿**（本套没拍完，继续 = 拍完这一套）：
- 封面机器比脸偏低（set_paused_likeness）：给用户看封面；说像 → `--resume` 续拍本套；说不像 → 改方案另起一套。
- 结果不确定（set_paused_unknown）：先核对set-status与调用记录，按实际set-record，再续拍本套未提交的张（Claude Code 用 generate-set --resume，Codex 按未提交的张逐张 compile-shot→原生生图→set-record）；不猜失败，不自动续跑。
- 比脸不可用（unavailable）：照常拍完，交付时说明这次没做机器比脸。
- Codex路径没有自动暂停：封面出来后宿主跑likeness-check，结果按上面同样处理。

## 可选机器比脸

露脸成图与本人照片的机器相似度，只用来提醒“先给用户比脸”，不判定像不像，也不能当验收。像不像以用户为准。

### 什么时候跑

- Claude Code：`generate-set` 拍完露脸封面（第 1 张）自动跑；分低就返回 `set_paused_likeness`，停在第 1 张。用户说像，再 `--resume` 续拍本套；不像就改方案另起一套，这张不当后几张的连拍参考。结果 unknown 先核对登记再续拍；`unavailable` 照常拍完，交付时说明没比脸。
- Codex 或单张重拍：`CLI likeness-check <图> --photo <本人照片> --workspace <ws>`，返回 `ok` / `low` / `no_face` / `unavailable` 和分数。
- 没装模型、OpenCV 缺这两个接口、或模型哈希不符时一律 `unavailable`，流程照常走，向用户说明“这次没做机器比脸”。

### 模型（不随 skill 分发，用户自行放置）

放到 `<workspace>/cache/face-models/`，或用环境变量 `SHY_CAMEO_FACE_MODELS` 指向目录。来自 OpenCV Model Zoo，脚本按 SHA-256 校验：

| 文件 | 来源 | 许可 | SHA-256 |
|---|---|---|---|
| `yunet.onnx` | opencv_zoo `face_detection_yunet_2023mar.onnx` | MIT | `8f2383e4dd3cfbb4553ea8718107fc0423210dc964f9f4280604804ed2552fa4` |
| `sface.onnx` | opencv_zoo `face_recognition_sface_2021dec.onnx` | Apache-2.0 | `0ba9fbfa01b5270c96627c4ef784da859931e02f04419c829e83484087c34e79` |

下载会访问外部网络，要用户同意后再下；比脸全程在本机，不上传照片。

当前提醒阈值为 0.83，只用于露脸封面；分数不能替代用户对本人感的判断，其他镜头不据此暂停。

## 生成临时定妆表（可选；额外图片，须用户明确要求，头部 / 全身各 1 次）

定妆表可选；不随套图自动生成；只有用户明确要求制作时才执行。

定妆表提示词由脚本编译（`compile-sheet`），两个宿主完全相同；不要自己拼提示词。

1. 沿用用户对本次定妆表的明确请求。头部、全身各算 1 次，逐张生成，失败不自动重试。
2. 头部：`CLI compile-sheet --character <卡片> --variant <时期> --sheet head --workspace WS`，拿到 R（`request_path`）。同一角色已有另一时期的头部定妆表时，可加 `--ref-variant <那个时期>`，让脸保持一致。
3. 生成：Codex 按本页“Codex 原生”用 R 生成；Claude Code 用 `CLI generate-exec --request R --workspace WS --authorized-count 1`。之后运行 `CLI verify --request R`。
4. 挂回卡片：`CLI attach-sheet --character <卡片> --variant <时期> --sheet head --image <生成的 PNG 原图> --workspace WS`。脚本按原字节复制，并把卡片状态改回 `temp_draft`。由 attach-sheet 自动完成：同时把该时期的神似检查重置为 pending（换了图就要重新检查）。
5. 全身：重复第 2–4 步，参数改为 `--sheet body`（自动参考本时期的头部定妆表，所以必须先挂好头部）。
6. 把两张定妆表给用户看：确认 → 把卡片 `status` 改为 `temp_confirmed`；不满意 → 重做（用户明确要求重做）或放弃该角色。
