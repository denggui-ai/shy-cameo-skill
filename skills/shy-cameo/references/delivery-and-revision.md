# 交付与修订

按需读：回答“完成了吗”看「状态词表」与「套图」；交付前看「出图后模型目视清单」；改图看「已认可画面的局部修订」。`sidecar.json` 是单张制作与验收记录，`QA` 指已执行的检查；二者均不能代替用户接受。

## 项目与系列

project-status从现有套图账本与选用版sidecar推导状态，不在project.json保存另一份完成标志。原版自动关联，重拍按索引候选关联；未选用新版不替换旧版验收。单套五张匹配交付且accepted才complete。本次selection所有套图complete才表示本次范围完成，不表示所有提案或未来系列完成。引用缺失/结果不一致为待整理；claimed不等于失败，也不自动恢复；generate-set遇结果未知时该张保持claimed、本次不再提交，核对后set-record，再--resume只拍未提交的张。套图账本缺失但已有首图文件或属于该套的request时，compile-shot、generate-set、set-status返回`ledger_missing`并停止，不按未开始重拍，也不自动重建为pending；先核对历史。格式与暂停规则见series-and-projects.md。

## 状态词表
| 对象 | 状态 | 含义 |
|---|---|---|
| 分镜卡 | `unverified` | 草稿 / 候选：模型现场生成，未经用户确认 |
| 分镜卡 | `user_confirmed` | 用户已确认，可以编译 |
| 分镜卡 | `gold` | 已验证分镜模板：经过真实出图验证，随 skill 分发 |
| 角色卡 | `temp_draft` | 临时角色文字造型草稿 |

| 角色卡 | `gold` | 库内已确认角色：已由维护者提升并随库分发；具体质量验证范围另列，状态本身不是法律或质量证明 |
| 单图审计 | `pass` | 唯一请求读取窗口内恰有一次可解析调用，提示词和参考路径与 request.json 一致 |
| 单图审计 | `unverifiable`（历史 `unverified`） | 无法审计：日志、唯一窗口或可解析参数不足；说明具体原因，可交付但不称已核验 |
| 单图审计 | `tampered` | 证据显示请求被改动或混入演员名，不建议公开发布 |
| 单图判定 | `pending` / `accepted` / `rejected` | 用户自检前 / 接受 / 拒绝（任一项回答“否”，含 --goal no，即 rejected） |
| 结果未知 | `failed_timeout` / `failed_no_image` | 超时 / 没拿到图，额度可能已扣，不自动重试；generate-set 中该张保持 claimed 并暂停，核对后才登记 |
| 首图待比脸 | `set_paused_likeness` | 露脸封面已生成并登记，机器比脸分低于阈值；后 4 张未提交，等用户比脸：像就 `--resume`，不像就改卡另起一套。机器分只是提醒，不等于“不像”，也不能当验收 |
| 阻断 | `blocked_consent` / `blocked_quota` / `blocked_name` / `blocked_platform_input` | 授权未确认 / 额度未授权或用完 / 演员名无法映射 / 平台拒绝 |

动画主题的离线编译通过不等于实际套图生成就绪或成片验收。`user_confirmed` 仅记录对相应分镜的确认，不能代替角色设计确认、成年人照片同意或本次生成意图。静态兼容测试使用合成夹具；实际候选卡不因此改为确认状态。

只有 `verdict: accepted` 的图才是用户接受的最终版本；临时定妆表和未自检的出图都只是候选。
`verdict` 由 `CLI record-verdict` 按用户自检的回答写入 sidecar（本人感、角色、异常三项必填，本次目标 --goal 可选），模型不得自行改写；用户没答到的项要问，不替用户填“没问题”。

## 完成标准（单张重拍或局部编辑）
适用于一套 5 张之外、对其中某一张重新授权 1 次的重拍或局部编辑；整套的完成标准见下方“套图（v4）”，两者都以 `verdict: accepted` 为准。`compile-edit` 仅写请求及参考摘要，不表示已提交、已交付或效果通过。
- 输入：`user_confirmed` 分镜卡及授权确认三项；普通重拍需`gold`或`temp_confirmed`角色卡及至少1张用户照片，局部编辑需已登记同意的指定底图和明确修改说明。
- 产物：`WS/outputs/<run_id>/request.json`、原图副本 `image.*`、`sidecar.json`；可选 `image-badge.png`。
- 检查：photo-check、frame-check、verify 都已运行；用户完成三项自检。
- 不得声称：没有用户自检就说“完成”；`audit: unverifiable` 或历史 `unverified` 时说“已核验”；把静态检查或 pytest 通过说成真实出图验证。

## 套图（v4）
| 对象 | 状态 | 含义 |
|---|---|---|
| 套图卡 | `unverified` / `user_confirmed` | 5 张分镜未确认 / 已确认 |
| 账本单张 | `pending` / `claimed` | 未提交 / 已编译待生成 |
| 账本单张 | `generated` / `rejected` / `failed` | 成功 / 平台拒绝 / 核对后确认失败（都计额度）；未核对的超时或无图保持 `claimed` |
| 账本单张 | `cancelled` | 第 1 张失败后取消，未提交、不计额度 |

**一套的完成标准**：
- 5 张都完成 deliver 与用户自检，且 `verdict: accepted`；
- 有失败或取消时，如实报告 `quota_used` 与每张的状态；
- 不得把部分完成说成完成。

## 出图后模型目视清单
1. 角色有没有露脸：正面朝向的人形、镜中正脸或剪影、脸部黑影都算不合格。
   同时检查角色存在感与主次关系：实际入镜的体态、毛色、服饰或物件是否足以支持所选角色，是否因贴近镜头占成巨大前景或为凑特征而突兀裁头；主角是否仍是视觉中心。两人的位置、视线与接触动作是否回应同一事件，背影角色是否实际参与。只出现无法辨认身份的普通手掌时，应如实标记辨识不足；不能只因不露脸或角色更大就判合格。用户明确选择极少入镜的细节镜头按其目标检查，不自动扩大角色或重拍。
2. 人体与动作：头颈、肩背、上臂、肘腕、手指是否合理连接；衣袖与包带是否掩盖断肢、重复肢体或错误交叉；躯干朝向、脸朝向、视线和交接动作是否相容。逐张放大原图看，不只看联系表缩略图：上身与胯、腿是否同一朝向（背影常被画成腿朝前），露脸张头转是否超过约 20°、眼睛是否斜着看（人体与头向）。
3. 道具：按 storyboarding.md 对照选物依据与人物身份、地点时代、用户指定的反差；比较物件与衣装、伙伴、环境的色彩反光和体量，确认主体与视觉焦点。跨图核对关键物件数量、归属、开合、消耗或明确修改，出框不等于丢失，重复出现不自动算重复构图。再检查实际物件、使用状态与已定活动是否一致，是否无故新增故事或抢过人物互动；再核对颜色、材质、长短与 `prop_specs`。按设计检查握持、搭放或桌面支撑，不要求所有道具入手；远景道具有没有失真发假。沿身体—上臂—前臂—手—道具检查前后、遮挡、接触和支撑是否一致，如演奏是否像反手绕到背后、手是否穿过器物。再检查可见结构与使用状态是否自洽，如摊开本子的书脊、两侧页块与封面是否连贯，手势是否误读成缺工具的操作。裁切或遮挡导致看不清时标为关系不清，不能直接断言画反，也不能仅凭道具名称判正确。结构画对不等于道具选对；局部编辑前后都检查，身份改善不能替代空间关系通过。
4. 空间与节拍是否符合已确认的玩法计划：本次实际确认的动作与节奏；首尾可复用，同景例外须已明确确认。指令是否照做：色调（黑白不是棕褐）、时辰（黎明不是夕阳）、人物性别、左右站位。
5. 多余元素：卡通图案混进戏服、时代不符的地标、`frame-check` 报 `extra_faces` 时有没有多出路人。
6. 主角的脸有没有被画得像某位真实演员（妆造往公认形象靠时尤其要看）；像就如实说明、不建议发布。
7. 用户要求真实机位时：逐张对照已记录的实景来源，检查地标、桥梁、岸线、台阶与遮挡关系；无法对应时标为机位未验证，不以城市名或地标名代替核实。
8. 造型修改同时检查三件事：仍可辨为本人、明确要求的变化可见成立、本次保留项没有明显附带漂移。收腰看不出变化不能因脸保留就判通过；换裙子却改了未授权的妆发需记录缺陷。遮挡或出框的身形、裙长、鞋款记未观察，材质外观不证明真实纤维。生成成功、模型目视通过与用户接受分别记录；平台拒绝或缺图不能算整套通过，不为补齐改词绕过拒绝。
发现问题如实告诉用户，区分已确认的画面缺陷与尚未查明的原因；不能直接归咎编译器，也不能把调用成功当画质通过。不自动重拍；用户明确指定重拍时才开始新任务。

开发案例集可分为待验收候选、用户已验收、问题与改进、历史案例。每组保留玩法、分镜、实际输出、检查结果和经验；成功展示以实际验收范围为准。案例页的编辑状态不能替代CLI的用户verdict；用户要求本地整理不等于远端发布。

`set_generated` 仅表示五张均生成，仍待 deliver 与用户验收；不是套图完成。CLI 接受最终 accepted 前要求本次审计、图片构图记录及交付摘要齐全且匹配；audit 可为已告知原因的 unverifiable，兼容历史 unverified；audit 为 tampered 时 record-verdict 拒绝正式 accepted（`audit_tampered`），sidecar 与 audit.json 原样保留为问题证据，仍可记 rejected，project-status 也不把此类接受计为完成。

## 摄影与输出来源

检查用户所选电影感/舞台/旅行/动画效果是否体现在镜头目的、光源、前中后景、动作、色彩与连续性中；具体见storyboarding.md。没有新图验证时只能说摄影方案与编译已验证，不宣称画质已修好。人体、真实机位和风格仍需目视核对。

PNG像素流检查与人脸检测分开；检测器缺失不放行坏PNG。audit pass限调用窗口参数与次数；图片/请求分别绑定哈希不等于图像服务输出来源已自动证明。CLI异常退出或旧图片路径不作为成功；保留结果待核查，不自动重试。当前原生输出关联仍需核对实际工具返回路径，未验证时如实标记。

## 本人感与素材覆盖

按本页“本人感评估记录”分别记录实际姿态、本人感绝对评价和组内相对偏好。助手认为更像、文件完整性通过、或用户只选相对较好的一张，都不能替代本人感通过；范围结论附输入包与样本条件，不外推为通用角度限制。私有研究记录不自动改写CLI verdict或已接受的旧版本。

## 道具验收

验收分别记录选物是否合适、视觉搭配是否成立、结构动作是否可信，不能互相代替。先判断整体活动是否合常理、道具是否真正发挥用途；整体不成立就判该项失败，不能被局部接得上或画面好看抵消，也不把明确矛盾降为遮挡未知。再放大实际参与动作或用户指出异常的局部：物件的部件连接、开合和厚度应自洽；持物须追溯肩—肘—腕—手—物件，不能止于“手碰到了物件”。写出支持判断的可见证据；正常衣袖遮盖不要求关节裸露，先看轮廓与姿态是否足以支持连接；关键连接仍无法判断时标“未验证”，不臆造隐藏关节，也不直接断言畸形。关键结构失败或未验证时，该图不能记整体通过；不因此自动重拍，按本次授权处理。跨图仍核对数量、归属和状态，修订后比较保留项是否漂移。图片存在、文字或代码测试通过、模型目视和用户接受分别记录。页面需要内容时允许不可辨读印刷或书写痕迹，不把书/剧本一律变空白，不承诺长正文精确生成。

示例只解释方法：阅读可用印刷书，记录可用本子，抱猫放空可以空手；暂停时不必握笔，写字时需有一致工具动作。不可将这些例子变成道具许可名单。

## 本人感评估记录

每张分别记录：实际输入及输出摘要、期望姿态、实际姿态是否符合、助手目视意见、用户是否觉得足够像。两图比较另记相对偏好；“右边更像但都不像”不能记为右图通过。

身份评价状态采用本私有评估记录的 `pending`（待用户评价）、`accepted`（用户明确认为足够像）、`rejected`（用户明确认为不够像）、`uncertain`（无法判断）。保留用户原话；与CLI正式交付verdict分开，不能自动提升整图或整套验收。

效果范围标为：`unverified`（无匹配验证证据）、`observed`（有实际样本但尚不能证明稳定）、`validated_for_scope`（有用户绝对验收与重复结果，且明确列出人物、输入包、输出条件、次数和局限）。这些是私有评估字段，不新增CLI账本状态；文件哈希/静态测试通过不能把效果范围提升为已验证。不从单个人推广到女性群体，不把AI模特视角当作真实身份真值。

## 已认可画面的局部修订

场景、构图与情节已获认可，而问题集中于脸部或少量配件时，优先考虑编辑现有图，避免为修脸重新生成整张。需要改变场景、机位或动作关系时再选择重拍；局部编辑不是所有缺陷的通用解法。先汇总剩余问题，不把汇总清单直接变成整套重生成任务；方法效果未定时，可提出一张有代表性的有限测试，具体张数仍按用户请求。

明确区分输入角色：待修成图用于保留画面，原始本人照片用于校正身份。目视两者，具体描述实际偏差，如脸部轮廓、眼形与间距、鼻口比例；不套用某位用户的圆眼、饱满面颊等特征到所有人。已通过的生成图可作效果对照，不能取代原照成为身份真值。不先归因素材不足，也不默认要求补照片。

编辑前先检查底图中身体、手部与关键道具的前后、遮挡和接触关系；认可场景方向不等于每处空间关系都已通过。明显错误或无法读清的关系不能列入“原样保留”，也不能仅凭预期动作替画面解释正确；如实指出疑点，区分保留的场景与待修的动作关系。若需同时调整身体、道具和遮挡，说明已超出单纯修脸，按实际范围选择局部重构或重拍，不擅自扩大本次编辑。用户已明确选定的其他定稿不因此重开。

编辑指令限定修改区域与保留项：身份修正适应现有头向、表情及场景光线，不直接复制自拍的视线或光照；保留已认可且本次无需修正的构图、衣装、动作、伙伴、道具与色调。用户已提出的小配件修正可合并，不顺带美化或改变身形；明确要求换装、妆发或身形调整时，按 storyboarding.md“从用户愿望到造型变化”落实，不用旧图对应约束抵消新目标。私有修订记录保留用户原话、具体变化、保留项、实际参考与结果；这些是制作记录，不增加用户必填字段。工具未提供确定性遮罩时，只说“请求局部编辑”，不承诺区域外像素完全不变。

结果同时核对本人感和附带变化：头向、视线、脸部光影、手部、衣装配件与背景是否漂移。未改好如实保留，不自动重试或扩大到其余图片。用户通过单张后，只选用该版本，不重开已接受的小缺陷；方法可作为后续修订候选，不能据此宣布其他角度、光线或整套锁脸稳定。后续图片仍以原始本人照片为身份依据，按已授权范围执行。

## 单张重拍

用户明确指定某张后保存新的确认卡，用compile编译新请求；需要同组衣装连续性时可加--chain-set <原套图卡>，该首图会校验账本和哈希。首图缺陷或用户换装时先选择是否保留，不能复制错误。Codex继续走原生工具→verify/frame-check/deliver；CLI适配才用generate-exec。新旧图片与审计记录分开保存，不替换历史验收。

## 局部编辑编译

用户明确修改现有图时，先按本页“已认可画面的局部修订”核对底图、原始身份参考与修改范围。保存对应的user_confirmed分镜修订卡；已有素材同意沿用，底图字节尚未登记时，用既有consent命令补录，不重复询问已有授权。

```bash
CLI compile-edit --scene S --image I --instruction '本次明确修改和保留项' --workspace WS
```

I是要修改的那张底图；该入口只引用I，保留修改说明，写标准request.json及reference-hashes.json。分镜卡提供版本关联与确认信息，不将原分镜的整套动作、景别或首图重新注入编辑提示词。只编译，不提交、不改旧图、不替用户验收。用户明确要求零生图编译验证时，在隔离工作区到此停止；编译通过不代表局部编辑效果或像素保持通过。

确有本次生图授权时，先按 series-and-projects.md 将新run_id与本次分镜卡登记为候选、保留原选版，再按 generation.md 原样读取请求、调用当前宿主一次、verify／frame-check／deliver及record-verdict；不自动重试。底图变化需按现有同意与参考摘要检查重新核对。调用来源无法核实时保留unverifiable，未生成或未验收不算complete。
